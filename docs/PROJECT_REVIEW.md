검토일: 2026-10-02 · 기준 커밋: `ab0306c` · 대상: 게임 코드, 저장, 실행 서버, 런처, 테스트, 배포 워크플로.

후속 작업: 2026-10-02에 R1–R4를 순서대로 수정하고 엔진·PC/모바일 회귀 테스트를 추가했다. R1의 재계산 대기는 기존 v1 저장 형식으로 보존하며, R3의 조기 복구 상태가 담긴 기존 저장에는 현재 미션 초기화를 안내한다. 현재 작업 순서는 [ROADMAP.md](ROADMAP.md), 검증 구성은 [VALIDATION.md](VALIDATION.md)에 기록했다. 아래 문제 설명과 코드 위치는 최초 검토 커밋을 기준으로 한 기록이다.

## 1. 현재 판단

이 프로젝트는 핵심 기능과 배포 경로가 갖춰진 고등학생용 보안 학습 시뮬레이터다. 원본 기획의 튜토리얼과 필수 미션 3개, 조사·원인 설명·방어·정상 기능 재검증, 힌트, 저장과 초기화가 구현되어 있다. Windows 포터블과 정적 웹 ZIP을 만드는 구성도 있다.

다음 버전의 중심은 **진행 보존과 키보드 조작을 안정화하고, 방어 전후의 근거를 비교하는 학습 경험을 완성하는 것**이다. 현재 규모에서는 HTML·CSS·JavaScript와 정적 호스팅이 목적에 맞는다. 프레임워크나 DB 도입의 필요성은 현재 코드에서 확인되지 않았다.

기능 구현과 교육적 검증은 구분해야 한다. 자동 테스트는 게임이 끝까지 동작함을 확인하지만, 입문자가 개념을 이해하는지와 목표 플레이 시간 30–45분은 아직 확인하지 못했다. 미션 화면의 5분·8–12분 표시는 기획상 예상값이다.

## 2. 구조와 유지할 부분

| 구성 | 현재 책임 | 평가 |
| --- | --- | --- |
| `src/missions.js` | 목표, 명령 목록, 보기, 힌트, 해설, 내장 데이터 | 교육 내용이 별도 파일에 모여 있어 수정하기 쉽다. |
| `src/engine.js` | 명령 해석, 상태 변경, 정책 시뮬레이션, 해시, 완료 판정 | DOM 의존성이 없어 핵심 상태 전이를 단위 테스트할 수 있다. |
| `src/storage.js` | 저장 구조 검사, 복원, 완료 조건 재판정 | 저장된 완료 플래그를 그대로 신뢰하지 않는 점이 적절하다. 오류 종류별 처리는 보완해야 한다. |
| `src/app.js` | 렌더링, 이벤트, 탭, 명령 실행, 저장 연동 | 현재 규모에 충분하다. 화면을 통째로 다시 만드는 방식은 포커스 문제를 일으킨다. |
| `run.py`, `scripts/serve.js` | 허용된 정적 파일 제공 | localhost 바인딩, 파일 허용 목록, CSP가 기획의 실행 경계를 뒷받침한다. |
| `launcher.py`, `scripts/`, `.github/workflows/` | 실행 창, 패키징, 웹 내보내기, 검증·릴리스 | 학교 PC에서 설치 부담을 줄이는 방향에 맞는다. 이번 검토에서 Windows 바이너리를 다시 빌드하거나 실행하지는 않았다. |

유지할 설계는 다음과 같다.

- 허용된 문법과 내부 식별자만 처리하고, 명령 입력으로 실제 네트워크나 임의 코드를 실행하지 않는다.
- 동적 출력은 `textContent`로 표시하고, 포트·로그인의 시뮬레이션과 SHA-256 실제 연산을 명시한다.
- 포트 전체 차단은 실패하고, 정상 로그인과 자료 서비스 유지도 완료 조건으로 판정한다.
- 정책 변경과 파일 복구는 검증을 무효화하며, 해시 복구 뒤에는 재계산을 요구한다.
- 힌트를 사용해도 감점하지 않고, 클라이언트 점수를 시험이나 보안 역량 인증으로 소개하지 않는다.

## 3. 수정 우선순위

### R1 · 높음 · 복원 중 연산 실패가 정상 저장을 삭제함

근거: `src/storage.js:34–50`, `src/engine.js:63–66`.

`loadGame()`은 저장 구조 검사와 해시 재계산을 같은 `try/catch`로 처리한다. 정상 저장이어도 복원 과정의 `crypto.subtle.digest()`가 실패하면 저장 손상으로 간주해 `removeItem(SAVE_KEY)`를 호출하고 튜토리얼 초기 상태를 반환한다.

완료한 4개 미션을 저장한 뒤 해시 API가 일시적으로 예외를 발생시키도록 주입해 재현했다. 결과는 `recovered: true`, 현재 미션 0, 완료 미션 0, 저장 키 삭제였다. 평상시 지원 환경에서의 해시 계산은 기존 테스트를 통과한다. 문제는 연산 실패를 처리하는 경로다.

수정 방향:

- JSON·스키마·진행 순서가 잘못된 경우와 실행 환경·해시 연산 실패를 구분한다.
- 연산 실패 시 원래 저장을 보존하고, 마지막 해시 검증을 대기 상태로 두며 재시도 안내를 제공한다.
- 게임 시작 시 Web Crypto 사용 가능 여부를 확인해 마지막 미션에서 처음 실행 조건을 알게 되는 상황을 줄인다.

완료 기준: 유효한 저장 복원 중 연산 실패를 주입해도 저장이 삭제되지 않고 앞 미션 진행을 유지한다. 기존 손상 저장 초기화와 복구 후 재계산 필수 조건도 계속 통과한다.

### R2 · 중간 · 설정·정답 변경 후 키보드 포커스가 사라짐

근거: `src/app.js:61–69`, `src/app.js:85–112`.

라디오 선택과 정책 변경이 `render()`를 호출하고, `replaceChildren()`이 조작 중인 입력 요소를 제거한다. 시스템 Chromium에서 라디오를 키보드로 선택하거나 8080 설정을 변경한 직후 `document.activeElement`가 `BODY`가 되는 것을 재현했다. 다음 키보드 조작이 현재 입력에서 이어지지 않는다.

수정 방향: 조작 중인 컨트롤은 유지하며 필요한 내용만 갱신하거나, 다시 렌더링할 때 같은 컨트롤로 포커스를 복원한다. 명령 실행 후 입력창으로 이동하는 의도적인 포커스 동작과 설정 변경은 구분한다.

완료 기준: 키보드만으로 설명 선택과 방어 설정을 연속 조작할 수 있다. 설정 변경 후 선택한 컨트롤에 포커스가 남고, 기존 탭 방향키 테스트도 통과한다.

### R3 · 중간 · 조사 전 파일 복구가 미션을 막다른 상태로 만듦

근거: `src/app.js:115–120`, `src/engine.js:68–74`, `src/engine.js:148`, `tests/engine.test.js:85–89`.

미션 3은 최초 해시 비교 전에도 복구 버튼을 사용할 수 있다. `budget.csv`를 먼저 복구하면 이후 해시가 전부 일치하므로 필수 조건인 `변경 감지 기록`을 얻을 수 없다. 현재 미션 초기화를 해야 다시 완료할 수 있다. 별도 재현에서도 유일한 미충족 항목이 변경 감지 기록이었다.

조사 기록 없이 완료시키지 않는 엔진 규칙은 타당하다. UI가 그 규칙을 행동 전에 알려줘야 한다.

수정 방향: 기준 출처와 변경을 확인하기 전에는 복구를 잠그고, 필요한 조사 행동을 안내한다. 이미 먼저 복구한 저장이 있다면 현재 미션 초기화로 다시 조사할 수 있음을 명확히 안내한다.

완료 기준: 초기 상태에서 바로 복구해 진행이 막히는 상황이 발생하지 않고, 정상적인 조사 → 복구 → 해시 재계산 흐름은 유지한다.

### R4 · 낮음 · 변경된 상태와 이전 검증 결과의 관계가 불명확함

근거: `src/engine.js:35–38`, `src/engine.js:68–73`, `src/app.js:124–127`.

정답 변경과 파일 복구는 `verified`를 해제하지만 `checks`를 지우지 않는다. 성공 후 정답을 바꾸면 완료 상태는 해제되어도 설정 탭에는 이전 검사 결과가 전부 통과로 남는다. `최근 재검증 결과`라는 제목상 과거 기록이지만, 현재 상태에 대한 검사인지 구별하기 어렵다.

수정 방향: 관련 상태가 바뀌면 검사를 비우거나, 이전 설정에서 수행한 결과임과 재검증 필요 상태를 함께 표시한다. 비교 기록을 추가한다면 검사 당시 정책을 저장하는 방법도 가능하다.

완료 기준: 정책·설명·파일 변경 이후 이전 성공 결과를 현재 상태의 성공으로 해석하지 않도록 화면에서 구분된다.

### R5 · 확장 직전 · 미션 데이터와 판정의 결합을 줄임

근거: `src/engine.js:17–21, 83, 97–102, 142–148`, `src/storage.js:5, 20, 39`, `src/app.js:72, 79, 85–123`.

미션 수 4, 인덱스 0–3, 파일명 `budget.csv`, 빠른 명령, 설정 UI가 여러 곳에 분산되어 있다. 새 미션 하나를 추가할 때 데이터 파일 외에도 엔진·저장·UI를 함께 바꿔야 한다. 현재 필수 미션에는 동작상 문제가 없지만 확장 시 누락 가능성이 커진다.

수정 방향: 미션 수는 `MISSIONS.length`로 계산하고, 미션 ID별 명령·판정·초기 환경·UI 구성을 정리한다. 먼저 반복되는 빠른 명령과 단서 정의부터 옮긴다. 저장 스키마 변경에는 기존 진행의 이관 또는 명시적인 버전 처리 정책을 포함한다.

완료 기준: 선택 미션 추가에 필요한 수정 위치와 저장 버전 영향이 명확하다. 실제 확장 계획이 생길 때 진행하며 현재 안정화보다 앞세우지 않는다.

## 4. 프로젝트 방향성

**학교 시연에 쓸 수 있는 가상 보안 조사 게임**을 다음 완성 목표로 잡는 것이 적절하다. 핵심 가치는 단서를 근거로 판단하고, 방어가 문제를 막으면서 정상 기능을 유지하는지 직접 확인하는 데 있다.

현재는 빠른 명령과 정답 선택, 설정 체크를 따라 끝낼 수 있다. 조작 접근성은 유지하되 다음 내용을 보강해 판단 과정을 드러내는 편이 좋다.

| 보강할 경험 | 구현 예 | 확인 방법 |
| --- | --- | --- |
| 방어 전후 근거 비교 | 8080 접근 상태와 443 정상 동작을 한 화면에서 비교 | 참가자가 무엇이 바뀌고 무엇이 유지됐는지 설명한다. |
| 정책 변화의 원인 이해 | 길이만 변경한 결과, 흔한 값 차단 추가 결과, 시도 제한 추가 결과 비교 | 길어도 흔한 값이 왜 거부되는지 설명한다. |
| 오답별 피드백 | 포트 전체 차단이나 해시로 신원 보장 선택 시 관련 관찰로 되돌리는 안내 | 정답을 외워 누르기보다 관찰 근거를 다시 확인한다. |
| 최종 조사 정리 | 발견한 문제·적용한 방어·정상 기능 재검증 결과를 미션별로 요약 | 종료 후 핵심 개념을 자신의 말로 설명한다. |

30–45분을 맞추기 위한 반복 입력이나 대기 시간은 추가하지 않는다. 입문자 시연에서 실제 소요 시간과 이해 정도를 먼저 확인하고, 필요한 학습 내용을 보강하거나 안내 시간을 현실에 맞춘다.

Windows 포터블과 HTTPS 정적 웹은 같은 게임 파일을 사용하는 두 배포 경로로 유지한다. 포트가 달라지면 브라우저 저장 출처도 바뀌는 현재 특성은 이미 배포 문서에 안내되어 있다. 실제 사용에서 필요가 확인되면 단일 실행 창 유도나 진행 내보내기·가져오기를 검토한다.

선택 암호 퍼즐은 필수 미션의 안정화와 사용성 확인 뒤 검토한다. 실제 서버 실습은 원본 기획대로 격리·복구·허용 범위를 갖춘 별도 단계로 둔다.

## 6. 이번 검토의 검증과 범위

- Node.js 24.19.0, Python 3.12.14에서 기존 엔진 테스트 18개와 Python 서버 테스트 4개 통과.
- 기존 PC·모바일 브라우저 테스트 6개는 시스템 Chromium 151.0.7922.173으로 통과.
- 기본 `npm run check`는 엔진·서버를 통과한 뒤 Playwright 전용 브라우저 파일 부재로 브라우저 테스트를 시작하지 못했다. 저장소 설정은 그대로 두고 `/tmp`의 검증 설정에서 시스템 Chromium 경로와 서버 작업 디렉터리를 지정해 기존 브라우저 테스트를 실행했다.
- 별도 임시 재현으로 정상 저장의 해시 복원 실패 시 삭제, 라디오·설정 변경 시 포커스 유실, 조사 전 파일 복구 이후 변경 감지 조건 미충족, 설명 변경 후 이전 검사 결과 유지 확인.
- 초기화 확인 후 다시 연 대화상자를 Escape로 취소하는 경로는 시스템 Chromium에서 진행을 보존했다. 이번 환경에서 오류로 재현되지 않아 수정 항목에 포함하지 않았다.
- 이번 검토에서 입문자 시연, Windows 실행 파일 재빌드·GUI 실행, Firefox·Safari·실기기·스크린리더, 홈서버 HTTPS 배포는 수행하지 않았다. 기존 문서의 Windows 검증 기록은 이번 실행 결과와 구분한다.
- 제품 코드와 기존 계획·검증 기록은 변경하지 않았다. 이 문서는 분석 결과와 후속 작업을 정리한 산출물이다.

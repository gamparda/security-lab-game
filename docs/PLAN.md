# 보안 체험 게임 개발 계획서

브라우저 시뮬레이터로 시작하는 입문용 프로젝트  
작성일 2026년 10월 2일

### 1 기획 방향

첫 버전은 외부 서버에 접속하지 않는 가상 보안 실습 게임으로 제작합니다. 플레이어가 단서를 조사하고, 취약한 설정의 원인을 설명한 뒤 방어 조치를 적용하고 다시 확인하는 과정을 익히도록 합니다. 완성 후 실제 통신을 배우는 로컬 실습을 별도 단계로 추가합니다.

안전성은 게임 화면의 유무보다 실제 네트워크 요청과 코드 실행 범위에 달려 있습니다. 모든 대상을 게임 데이터로 처리하는 1번은 사고 범위를 줄이기 쉽습니다. 2번도 본인이 소유하거나 명시적으로 허가받은 실습 서버를 격리하면 가능하지만, 접근 통제와 초기화까지 운영해야 합니다. [1]

| 판단 기준 | 1번 가상 환경 게임 | 2번 실제 실습 서버 |
| --- | --- | --- |
| 학습 효과 | 단서 분석과 보안 개념을 단계적으로 설명하기 좋음 | 실제 HTTP 요청과 서버 동작을 직접 관찰할 수 있음 |
| 개발 부담 | 명령어 해석기와 미션 로직 중심 | 취약한 앱 구축과 격리 및 복구 작업 필요 |
| 안전성 | 외부 접속과 임의 실행을 없애면 상대적으로 높음 | 실제 취약점이 있으므로 노출 범위 통제가 필요 |
| 한계 | 실제 도구와 네트워크 동작을 숙달하기 어려움 | 설치 문제와 운영 부담이 입문 학습을 방해할 수 있음 |
| 권장 시점 | 첫 작품과 학교 시연 | 첫 버전 완성 후 개인 로컬 실습 |

### 2 대상과 완료 목표

대상은 보안을 처음 접하는 고등학생입니다. 제작자가 변수, 조건문, 반복문, 함수의 기초를 알고 있다고 가정합니다. 개발은 1인 기준 주 5~7시간씩 6주, 총 30~42시간을 계획합니다. 기초 프로그래밍부터 배우는 경우 준비 기간 2~4주를 추가합니다. 일정은 견적이며 숙련도에 따라 조정합니다.

완료 목표는 튜토리얼과 필수 미션 3개, 30~45분의 플레이, 저장과 초기화, 3단계 힌트, 미션별 방어 재검증입니다. 첫 버전에는 회원가입, 온라인 순위, 실시간 멀티플레이, 임의 코드 실행을 넣지 않습니다.

## 3 미션 구성과 학습 목표

가상의 학교 동아리 자료 서버에서 이상 징후가 발견됐다는 이야기로 시작합니다. 플레이어는 사전 승인된 조사 담당자이며, 모든 계정과 문서와 서버는 게임용 가상 데이터입니다. 각 미션 화면에 실제 연산과 시뮬레이션의 경계를 표시합니다.

| 미션 | 플레이어 행동 | 구현과 학습 내용 | 완료 조건 |
| --- | --- | --- | --- |
| 튜토리얼<br>5분 | help와 inspect를 사용해 단서 찾기 | 명령어 입력과 결과 읽기<br>허용된 조사 범위 이해 | 단서 1개 발견 후 조사 범위 선택 |
| 1 노출된 서비스<br>8~12분 | 가상 서버를 scan하고 불필요한 서비스를 찾아 설정 수정 | 포트 상태는 시뮬레이션<br>열린 포트와 취약점의 차이 | 불필요한 포트 차단과 필수 서비스 정상 동작 확인 |
| 2 약한 로그인 정책<br>8~12분 | 제공된 더미 후보와 시도 기록을 비교하고 정책 수정 | 후보 대입은 시뮬레이션<br>길이와 흔한 값 및 시도 제한 이해 | 차단 목록과 제한 적용 후 정상 로그인 및 반복 시도 확인 |
| 3 변조된 자료<br>8~12분 | 세 파일의 SHA-256을 신뢰 가능한 기준값과 비교 | 브라우저에서 해시 실제 계산<br>변경 탐지와 신뢰 기준 이해 | 바뀐 파일 확인 후 원본 복구와 일치 검증 |
| 선택 미션 암호 퍼즐<br>10분 | 시저 또는 반복 키 XOR를 해독하고 한계 설명 | 장난감 암호 실제 연산<br>암호화와 해시 구분 | 복호화 성공과 실사용 부적합 이유 설명 |

### 미션 1에서 오해를 막는 방식

포트가 열려 있다는 사실만으로 서버를 취약하다고 판정하지 않습니다. 서비스 설명과 운영 목적을 함께 제공합니다. 예를 들어 필수 웹 서비스는 유지하고 불필요한 관리 서비스만 제한해야 정답입니다. 포트를 모두 닫으면 웹 서비스도 실패해 미션을 완료할 수 없습니다.

### 미션 2에서 오해를 막는 방식

특수문자의 개수만으로 강도를 판정하지 않습니다. 짧고 흔한 비밀번호에 기호를 붙여도 안전하다고 단정할 수 없습니다. 최신 NIST 지침은 길이와 흔하거나 유출된 값의 차단을 중시하며 문자 종류 혼합을 일률적으로 강제하지 않습니다. 강도 점수는 교육용 추정이며 실제 유출 여부나 해독 시간을 보장하지 않습니다. [2]

### 미션 3에서 오해를 막는 방식

해시가 다르면 데이터가 변경된 것이지만 악성코드라는 뜻은 아닙니다. 해시가 같더라도 비교 기준이 공격자에게 바뀌었다면 신뢰할 수 없습니다. 단순 SHA-256을 비밀번호 저장 방식으로 소개하지 않으며, 이 용도에는 Argon2id 등의 별도 알고리즘이 필요하다고 설명합니다. [3]

## 4 플레이 흐름과 화면 구성

### 진행 흐름

임무 설명 → 단서 조사 → 가설 선택 → 취약 상태 확인 → 방어 적용 → 같은 조건으로 재검증 → 결과와 해설 확인 순서로 진행합니다. 실패 시 정답을 바로 보여주지 않고 현재 관찰한 사실과 다음에 확인할 대상을 안내합니다.

### 화면 구성

상단에는 현재 미션과 진행 상태를 표시합니다. 중앙에는 가상 터미널, 서비스 목록, 파일 비교 결과를 탭으로 배치합니다. 옆 패널에는 임무 목표와 확보한 단서를 표시하며, 하단에는 힌트와 초기화 버튼을 둡니다. 작은 화면에서는 옆 패널을 아래로 옮깁니다. 색상만으로 성공과 실패를 구분하지 않고 텍스트도 함께 제공합니다.

### 첫 미션의 실제 플레이 예시

단서: 동아리 자료를 제공하는 웹 서비스와 더 이상 쓰지 않는 관리 서비스가 함께 실행 중입니다. “자료 서비스는 계속 사용할 수 있어야 한다”는 운영 조건을 제시합니다.

입력 예시: scan club-server  
결과 예시: 443 OPEN 자료 서비스 / 8080 OPEN 사용하지 않는 관리 서비스  
후속 입력: inspect club-server 8080  
조치: 설정 패널에서 8080 접근을 차단합니다.  
재검증: 다시 scan한 결과와 자료 서비스 접속 테스트를 함께 확인합니다.

위 명령어는 게임 전용 문법입니다. 실제 네트워크 스캐너나 운영체제 명령을 실행하지 않으며 club-server는 게임 내부 식별자입니다. “방화벽 차단”은 서비스를 종료하는 것과 다름을 해설에 표시합니다.

### 힌트와 점수

힌트는 1단계 개념, 2단계 확인할 위치, 3단계 다음 행동 순서로 제공합니다. 힌트 사용에 따른 감점은 두지 않고 사용 단계를 결과에 표시합니다. 속도와 반복 시도 횟수로 실력을 평가하지 않습니다.

| 평가 항목 | 배점 | 판정 방식 |
| --- | --- | --- |
| 단서와 문제 발견 | 30점 | 관련 단서를 확보하고 문제 대상을 고름 |
| 원인 설명 | 20점 | 설명 보기 중 근거와 일치하는 항목 선택 |
| 방어 적용 | 30점 | 필수 서비스를 유지하며 정책을 수정 |
| 재검증 | 20점 | 취약 동작이 차단되고 정상 동작은 유지됨 |

미션 완료에는 방어 적용과 재검증이 필수입니다. 점수는 학습 피드백이며 실제 보안 역량을 인증하는 지표로 사용하지 않습니다. 전체 완료 후 원인과 대응과 검증을 요약한 결과 화면을 제공합니다.

## 5 기술 설계와 안전 경계

### 권장 기술

첫 버전은 HTML과 CSS와 JavaScript로 만들고 프레임워크와 데이터베이스를 생략합니다. 정적 파일을 localhost에서 제공하고 실행 중 게임의 입력이 외부로 전송되지 않도록 합니다. 해시 계산은 Web Crypto API의 digest를 사용하며 HTTPS 또는 신뢰 가능한 localhost 환경에서 검증합니다. [4]

Python을 먼저 배우고 싶다면 동일한 미션 엔진을 콘솔 프로그램으로 먼저 만들고 화면을 나중에 붙이는 대안이 있습니다. 다만 첫 버전에 웹 프런트엔드와 Python 백엔드를 동시에 도입하면 구현 범위가 커집니다. Python 소켓 실습은 실제 통신을 배우는 다음 단계에 배치합니다.

| 모듈 | 책임 | 대표 데이터 |
| --- | --- | --- |
| 명령어 해석기 | 정해진 문법과 대상 식별자를 확인 | help / inspect / scan / hash / verify |
| 가상 환경 엔진 | 상태에 따라 결과를 계산 | 서버와 포트 및 접근 정책 |
| 미션 엔진 | 진행 조건과 힌트 및 점수를 관리 | 미션 ID와 단계 및 충족 조건 |
| 연산 모듈 | 파일의 해시 실제 계산 | 내장 더미 파일의 바이트 배열 |
| 화면과 저장 | 결과 표시와 진행 복원 및 초기화 | 미션 ID와 단계 및 힌트 사용 기록 |

### 상태와 판정 설계

미션 상태는 준비, 조사, 취약 상태 확인, 방어 적용, 검증 완료로 나눕니다. 완료 버튼이나 고정된 출력 문자열만 확인하지 않고 현재 정책과 정상 서비스 동작 등 실제 게임 상태를 판정합니다. 초기화는 미션의 원본 상태와 진행 기록을 함께 복구합니다.

미션 데이터에는 id, 목표, 초기 상태, 허용 명령, 단서, 힌트 3개, 완료 조건, 해설을 넣습니다. localStorage에는 진행 정보만 저장하며 실제 비밀번호와 개인 파일은 받지 않습니다. 클라이언트 코드에서 정답을 확인할 수 있으므로 공정한 시험이나 경쟁 대회 용도로 쓰지 않습니다.

### 입력 처리의 필수 규칙

명령은 허용 목록으로 해석하고 eval, Function 생성자, 운영체제 셸에 넘기지 않습니다. 사용자가 넣은 URL이나 IP로 fetch 또는 소켓 요청을 만들지 않습니다. 출력은 textContent로 표시해 입력 문자열이 HTML로 실행되지 않게 합니다. 입력 길이는 200자로 제한하고 모르는 명령은 오류 메시지로 처리합니다.

포트 상태와 로그인 공격은 시뮬레이션이며, 해시와 장난감 암호는 실제 연산이라고 화면에 명시합니다. 브라우저 개발자 도구의 네트워크 기록으로 게임 명령이 외부 요청을 생성하지 않는지 확인합니다. 새로운 미션이 네트워크 기능을 추가하면 이 경계부터 다시 검토합니다.

## 6 개발 일정과 검증 기준

필수 미션 3개가 끝까지 동작하기 전에는 암호 미션이나 디자인 효과를 추가하지 않습니다. 막히면 화면 장식과 점수 세부 항목을 줄이되 방어 적용과 재검증은 유지합니다.

| 주차 | 주요 작업 | 주말에 확인할 산출물 |
| --- | --- | --- |
| 1주 | JS 기초 확인과 화면 초안 및 미션 데이터 작성 | help와 알 수 없는 명령 처리가 되는 터미널 |
| 2주 | 가상 포트 상태와 설정 변경 및 재검증 구현 | 첫 미션을 설명부터 완료까지 플레이 가능 |
| 3주 | 더미 비밀번호와 후보 시도 및 정책 모델 구현 | 시도 제한 전후와 정상 로그인을 비교 가능 |
| 4주 | 내장 파일과 SHA-256 비교 및 원본 복구 구현 | 한 글자 변경을 탐지하고 복구를 검증 가능 |
| 5주 | 튜토리얼과 힌트 및 저장과 전체 초기화 구현 | 새로고침 후 복원되고 미션 순서가 연결됨 |
| 6주 | 입문자 시연과 오류 수정 및 설명서 작성 | 게임 파일과 실행법 및 테스트 기록 완성 |

### 기능과 안전 검증

① 미등록 명령과 외부 IP와 URL을 입력해도 네트워크 접속이 생기지 않습니다. ② HTML 태그나 스크립트처럼 보이는 입력은 실행되지 않고 텍스트로 표시됩니다. ③ 빈 입력과 긴 입력은 오류 안내 후 계속 플레이할 수 있습니다.

④ 서비스 전체 차단은 정상 기능 실패로 판정합니다. ⑤ 시도 제한을 적용한 상태에서도 정상 사용자의 첫 로그인은 성공합니다. ⑥ 해시 비교는 동일한 바이트에 같은 값을 반환하고 한 바이트가 바뀌면 변경을 탐지합니다. ⑦ 초기화 뒤에는 이전 조치와 점수가 남지 않습니다.

확인은 수동 시연과 미션 엔진의 핵심 상태 전이 테스트로 수행합니다. 저장 데이터 손상 시 진행 초기화를 안내합니다. 브라우저 개발자 도구에서 런타임 오류와 외부 요청을 확인하고 PC 및 모바일 화면을 한 번씩 점검합니다.

### 입문자 사용성 검증

가능하면 3~5명에게 시연합니다. 절반 이상이 3단계 힌트 없이 미션 1을 끝내는지, 종료 후 “열린 포트는 모두 취약점인가”, “해시 일치는 무엇을 보장하는가”를 설명할 수 있는지 확인합니다. 이는 소규모 사용성 확인이며 교육 효과를 통계적으로 입증하는 실험은 아닙니다.

### 예산과 제출물

기존 PC와 브라우저를 사용하므로 추가 하드웨어 구매는 필요하지 않습니다. 유료 API와 클라우드 서버도 첫 버전에는 불필요합니다. 신규 유료 서비스를 사용하지 않는다는 전제에서 추가 서비스 비용 목표는 0원이며 개발 시간은 별도입니다.

최종 제출물은 게임 원본, 실행 안내, 미션별 학습 목표와 시뮬레이션 범위, 검증 결과, 알려진 한계입니다. 시연 영상은 3~5분으로 단서 확인부터 방어 재검증까지 한 미션을 보여줍니다.

## 7 실제 서버 실습으로 확장하는 방법

### 2번 방식의 개발 범위

실제 요청과 서버 로그를 관찰해야 할 때 별도 실습을 추가합니다. 첫 주제는 개인 로컬 VM 안의 의도적으로 취약한 웹 앱 1개와 미션 1개로 제한합니다. 외부에 공개하는 취약한 서버는 첫 확장 범위에서 제외합니다. WebGoat 같은 교육용 앱도 실행 시 취약해지므로 노출을 줄여야 한다고 공식적으로 안내합니다. [1]

가이드에는 실행 대상과 허용 행위, 환경 설치, 초기 스냅샷, 정상 요청 관찰, 취약 동작 확인, 원인 해설, 방어 조치, 재시험, 종료와 복원을 순서대로 넣습니다. 기존 교육 플랫폼을 사용할 때는 해당 실습 환경과 이용 범위에 맞춰 작성합니다.

### 격리 환경의 완료 조건

VM의 네트워크는 내부 전용으로 설정하고, 브리지 연결과 외부 포트 전달을 사용하지 않습니다. 취약한 앱을 구동한 뒤 외부 통신이 차단되는지, 다른 기기에서 접근되지 않는지 확인합니다. 실제 계정과 문서를 넣지 않고 호스트의 개인 폴더도 연결하지 않습니다. Docker만 사용한다고 완전한 격리가 보장된다고 설명하지 않습니다.

초기 상태로 복원되는지와 자원 사용이 제한되는지 확인한 후 미션 가이드를 만듭니다. 이 조건을 마련하기 어렵다면 1번을 유지하고 실제 통신 학습은 별도의 허가된 워게임에 연결합니다. 확장 일정과 비용은 앱 선정과 격리 검증 이후 따로 산정합니다.

### 기초 자료에서 보완할 부분

시저 암호와 반복 키 XOR는 암호의 개념을 배우는 퍼즐로 다룹니다. 실제 데이터 보호 방식으로 소개하지 않습니다. 실사용 확장에서는 검증된 라이브러리와 AES-GCM 같은 인증된 암호화 방식을 학습하며 직접 암호 알고리즘을 설계하지 않습니다. [5]

OSI 7계층 전체를 암기한 뒤 개발을 시작할 필요는 없습니다. 첫 미션에는 IP와 포트 및 서비스의 관계를, 다음 미션에는 요청과 응답 및 로그인 정책을 필요한 만큼 설명합니다. 실제 서버 단계에서 HTTP와 운영체제 권한 및 로그 관찰을 추가합니다.
